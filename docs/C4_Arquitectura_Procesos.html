1. Modelo C4

1.1 Contexto del Sistema (C1)

PuraLino es una tienda en línea de ropa y artículos para el hogar fabricados en lino. Los usuarios (clientes y administradores) interactúan con una SPA (Single Page Application) construida con HTML5 y ES Modules, que se comunica con una API REST desplegada en Render, respaldada por MongoDB Atlas como base de datos, Cloudinary para gestión de imágenes, Brevo para correos transaccionales y Mercado Pago como pasarela de pagos.

1.2 Contenedores (C2)

ContenedorTecnologíaDescripción
Frontend SPA HTML5 + ES Modules + CSS Aplicación de página única con patrón MVC puro, desplegada como sitio estático en GitHub Pages
Backend API Node.js + Express.js API REST con autenticación JWT, desplegada en Render
Base de Datos MongoDB Atlas (Mongoose ODM) Persistencia de datos: usuarios, productos, pedidos, inventario
Cloudinary Cloud CDN + API Almacenamiento y entrega de imágenes de productos
Brevo HTTP API (SMTP relay) Envío de correos transaccionales (verificación, pedidos, tracking)

2. Decisiones de Arquitectura

#DecisiónJustificación
DA-1 Patrón MVC puro en el frontend sin frameworks Demuestra comprensión del patrón arquitectónico sin depender de abstracciones de terceros (React, Angular, Vue); reduce dependencias y tamaño del bundle; cada capa (Model, View, Controller) tiene responsabilidades bien definidas
DA-2 Patrón Observer (Event Bus) para comunicación entre capas Desacopla Model, View y Controller; permite que cambios de estado se propaguen sin dependencias directas entre componentes; la clase Observer con instancia global bus facilita la extensibilidad
DA-3 Patrón Strategy para pagos y descuentos Permite agregar nuevos métodos de pago o tipos de descuento sin modificar el código existente (principio Open/Closed); cada estrategia encapsula su propia lógica de validación
DA-4 API REST separada del frontend Separación de responsabilidades; permite escalar frontend y backend independientemente; despliegue en diferentes servicios (GitHub Pages vs Render); facilita desarrollo en paralelo
DA-5 JWT (JSON Web Token) para autenticación stateless No requiere sesiones en servidor; token autocontenido con {id, role, name}; expiración configurable (2h); compatible con arquitectura REST sin estado
DA-6 MongoDB con Mongoose como base de datos Schema flexible ideal para productos con variantes; modelado natural de documentos embebidos (items dentro de orders); Mongoose provee validación y tipado a nivel de esquema; escalabilidad horizontal nativa
DA-7 Mercado Pago Payment Brick para pagos Formulario de pago embebido que maneja tokenización PCI-compliant; evita manejo directo de datos de tarjeta en nuestro código; soporte para sandbox/pruebas; adaptado al mercado colombiano
DA-8 Brevo HTTP API para emails transaccionales Servicio confiable con alta deliverability; templates HTML personalizados con diseño corporativo; patrón fire-and-forget para no bloquear el flujo principal; 10 tipos de correo implementados
DA-9 Cloudinary para gestión de imágenes CDN global para entrega rápida; transformaciones automáticas; upload desde backend con Multer; evita almacenamiento local de archivos binarios en el servidor
DA-10 PWA con Service Worker Caché de assets estáticos para carga rápida y experiencia offline básica; manifest.json para instalación en dispositivos móviles como app nativa; versionamiento de caché para actualizaciones controladas
DA-11 Middleware de autorización por capas Seguridad en capas: primero authRequired (autenticación), luego adminOnly (autorización); separación clara de permisos cliente/admin a nivel de ruta
DA-12 Limpieza de datos sensibles en logout y entre sesiones Borrado de formularios, tokens y datos de pago del DOM y localStorage al cerrar sesión; reset completo del formulario de pedido al abrirlo; previene filtración de datos entre sesiones de diferentes usuarios

3. Procesos del Sistema

3.1 Proceso: Login y Autenticación de Usuarios

Objetivo: Permitir a los usuarios registrarse, verificar su identidad por correo electrónico, iniciar sesión de forma segura y gestionar la recuperación de contraseña, garantizando que solo usuarios autenticados y verificados puedan acceder a funcionalidades protegidas (compras, cuenta personal, panel administrativo).

El proceso incluye:

1. Registro de usuario

  • El cliente ingresa nombre, correo electrónico, nombre de usuario y contraseña
  • Validaciones frontend: campos obligatorios, formato de email, longitud mínima de usuario (3 caracteres), contraseña de al menos 6 caracteres con 1 mayúscula y 1 número
  • Validaciones backend: mismas reglas + verificación de duplicidad de username y email en la BD
  • Se genera hash bcrypt del password con 10 salt rounds
  • Se genera token criptográfico aleatorio de verificación de email (crypto.randomBytes(32))
  • Se crea el usuario en MongoDB con emailVerified: false y rol client
  • Se envía email de verificación vía Brevo HTTP API (fire-and-forget, no bloquea el registro)
  • Aceptación obligatoria de Términos y Condiciones mediante checkbox vinculado al botón de registro

2. Verificación de correo electrónico

  • El usuario recibe un email con enlace al endpoint GET /auth/verify-email?token=...
  • El backend busca usuario con token válido y no expirado (vigencia: 24 horas)
  • Si es válido: actualiza emailVerified: true y limpia tokens de verificación
  • Renderiza página HTML de éxito con diseño corporativo y redirección automática (5s) al frontend
  • Si el token es inválido o expirado, muestra página de error con opción de reenvío

3. Inicio de sesión (Login)

  • El cliente ingresa usuario o correo electrónico y contraseña
  • Backend busca por username O email (query $or de MongoDB)
  • Compara password con hash almacenado usando bcrypt.compare
  • Si es válido: genera JWT con payload { id, role, name } y expiración de 2 horas
  • Retorna token + datos del usuario (excluyendo passwordHash por seguridad)
  • Frontend almacena token en localStorage y lo adjunta como Bearer en cada request HTTP
  • Al recargar la página, se restaura sesión automáticamente invocando GET /auth/me con el token guardado
  • Si el token es inválido/expirado, se limpia sesión; si hay error de red, se usa caché local del usuario

4. Gestión de sesión y timeout por inactividad

  • Se monitorean eventos de actividad del usuario: mouse, teclado, scroll, touch, clicks
  • Timeout configurable (por defecto 30 minutos de inactividad)
  • Aviso visual 10 segundos antes de que expire la sesión
  • Al expirar: logout automático, limpieza de datos sensibles del DOM y localStorage, redirección al inicio
  • Cada interacción del usuario reinicia el temporizador de inactividad

5. Recuperación de contraseña

  • El cliente solicita reset ingresando su correo electrónico
  • Backend genera token criptográfico de reset con expiración de 1 hora
  • Se envía email con enlace al formulario de reset (renderizado por el backend como HTML)
  • El cliente ingresa nueva contraseña; se valida, hashea con bcrypt y actualiza en la BD
  • Tokens de reset se limpian tras uso exitoso
  • Por seguridad, no se revela si el email existe o no en la respuesta al usuario

6. Reenvío de verificación

  • Si el usuario no verificó su email, puede solicitar reenvío desde su perfil
  • Se genera nuevo token de verificación y se envía nuevo correo electrónico
  • El token anterior queda invalidado al ser reemplazado

7. Control de acceso (Autorización)

  • Middleware authRequired: verifica JWT en header Authorization: Bearer <token>; rechaza con 401 si es inválido
  • Middleware adminOnly: verifica que req.user.role === 'admin'; rechaza con 403 si no es administrador
  • Usuarios sin email verificado no pueden crear pedidos (validación adicional en endpoints de pagos/pedidos)
  • Datos sensibles del usuario anterior se limpian del DOM al cerrar sesión

3.2 Proceso: Proceso de Pedido

Objetivo: Permitir a los usuarios autenticados y verificados seleccionar productos, configurar opciones de envío, aplicar descuentos, realizar el pago (integrado con Mercado Pago) y recibir confirmación del pedido con factura, garantizando la integridad del inventario y la trazabilidad completa del pedido.

El proceso incluye:

1. Gestión del carrito de compras

  • El cliente navega el catálogo de productos con paginación (12 productos por página)
  • Selecciona talla y color (variantes) antes de agregar al carrito
  • Validación de stock disponible al momento de agregar (tanto stock general como por variante)
  • Carrito persistido en localStorage con timestamp; expira automáticamente a las 24 horas
  • Aplicación de códigos promocionales con descuento porcentual validado contra la BD
  • Visualización en modal del carrito: items, cantidades, subtotal, descuento aplicado y total

2. Formulario de checkout

  • Requiere usuario autenticado con email verificado (se valida antes de abrir el formulario)
  • Prefill automático de nombre, email, dirección y teléfono desde el perfil del usuario actual
  • Campos del formulario: nombre completo, email, dirección línea 1 y 2, departamento (dropdown dinámico con 33 departamentos de Colombia), ciudad (se carga según departamento), código postal, cédula, teléfono
  • Cálculo de costo de envío por ciudad (endpoint GET /shipping/quote?city=...)
  • Aplicación opcional de tarjeta de regalo con validación de saldo
  • Aceptación obligatoria de Términos y Condiciones para habilitar el botón de pago
  • Reset completo de todos los datos sensibles (pago, tarjeta, método) al abrir el formulario — previene filtración entre sesiones

3. Selección de método de pago

  • Tarjeta crédito/débito: campos de número, expiración y CVV con validación vía patrón Strategy
  • Mercado Pago: inicialización del Payment Brick embebido con el monto aproximado del pedido; el Brick maneja la UI de captura de datos de tarjeta de forma PCI-compliant
  • PayPal, PSE, Contraentrega: validación básica según cada estrategia
  • Al seleccionar Mercado Pago, se oculta el botón de submit estándar; el Payment Brick tiene su propio botón de pago
  • Al cambiar de método, se destruye el Brick anterior y se restaura el botón estándar

4. Procesamiento de pago con Mercado Pago

  • Frontend: el Payment Brick tokeniza los datos de tarjeta (PCI-compliant, nunca tocan nuestro código)
  • Callback onSubmit: lee campos del formulario de envío, valida completitud, construye payload con token + datos de pedido
  • Mapeo de campos snake_case del Brick (issuer_id, payment_method_id) a camelCase del backend
  • Backend POST /payments/process:
    • Valida usuario verificado, dirección, teléfono, ciudad, items no vacíos
    • Consulta productos en BD y valida stock de cada item/variante
    • Calcula subtotal sumando precio × cantidad de cada item
    • Aplica promociones (descuento porcentual), calcula envío por tarifa de ciudad, aplica gift cards
    • Crea la orden en MongoDB con estado pendiente_pago
    • Llama a la API de Mercado Pago con el token de tarjeta para crear el pago
    • Modo sandbox disponible (MP_SANDBOX=true) para simulación en entorno de desarrollo

5. Confirmación y post-procesamiento

  • Si pago aprobado:
    • Estado del pedido se actualiza a confirmado
    • Se decrementa stock de cada producto/variante en la base de datos
    • Se registra movimiento de inventario (StockMovement) de tipo "venta"
    • Se envía email de confirmación de pedido al cliente (con detalle de items y dirección)
    • Se envía email con factura detallada
    • Frontend: limpia carrito de localStorage, cierra modal, muestra toast de éxito
    • Se genera y muestra factura en modal con datos completos del pedido
  • Si pago pendiente o rechazado:
    • Se notifica al usuario con mensaje apropiado (pendiente/error)
    • Se limpia carrito y cierra modal de pedido

6. Generación de factura

  • Número de factura único generado con timestamp (FAC-{timestamp})
  • Se almacena en la orden (BD) y en localStorage del cliente para acceso offline
  • Renderizado en modal con datos completos: datos del cliente, dirección de envío, tabla de productos, subtotal, descuentos, envío, gift card y total
  • Opción de descarga como PDF profesional generado con jsPDF: encabezado corporativo, tabla de items con filas alternadas, sección de totales, pie de página

7. Gestión post-venta del pedido

  • Actualización de estado (admin): confirmado → enviado → entregado, con notificación por email al cliente en cada cambio
  • Tracking: asignación de número de guía y transportadora; registro de eventos de envío con fecha, estado y notas
  • Notificaciones automáticas: email al cambiar estado del pedido y al registrar eventos de tracking
  • Historial de compras: el cliente consulta sus pedidos con detalle completo, puede ver factura y rastrear envío con línea de tiempo visual
  • Devoluciones: solicitud dentro de 30 días posteriores a la entrega; flujo completo: solicitud → aprobación/rechazo → envío del cliente → recepción en bodega → revisión de calidad → generación de cupón (si apta); con notificaciones por email en cada etapa
