1. Plan de Gestión de Calidad

El presente plan establece las directrices, métricas y mecanismos de control de calidad para los dos procesos principales del sistema PuraLino E-Commerce:

Proceso 1: Login y Autenticación de Usuarios

Abarca el registro de nuevos usuarios con validación de datos, verificación de correo electrónico mediante token criptográfico, inicio de sesión por usuario o email con contraseña hasheada (bcrypt), emisión y verificación de tokens JWT, gestión de sesión con timeout por inactividad, recuperación de contraseña y control de acceso basado en roles (cliente/administrador). El objetivo de calidad es garantizar que la autenticación sea segura, confiable y con experiencia de usuario fluida, protegiendo los datos sensibles en todo momento.

Proceso 2: Proceso de Pedido

Comprende la gestión del carrito de compras con persistencia y expiración, formulario de checkout con datos de envío geográficos de Colombia, cálculo de costos de envío, aplicación de promociones y tarjetas de regalo, selección y procesamiento de pago (integrado con Mercado Pago Payment Brick), generación de factura con descarga PDF, decrementación automática de inventario, envío de correos de confirmación y gestión post-venta (tracking, actualizaciones de estado, devoluciones). El objetivo de calidad es asegurar que el flujo completo de compra sea correcto, seguro en el manejo de datos de pago, confiable bajo diferentes condiciones de red y con una experiencia intuitiva para el usuario final.

2. Calidad del Software

En el contexto de PuraLino, calidad significa que el software cumple de manera verificable con las expectativas de tres grupos de interés:

Clientes (compradores)

Esperan un proceso de registro e inicio de sesión rápido, seguro y sin fricciones. Necesitan que sus datos personales y financieros estén protegidos. Requieren un flujo de compra claro, donde puedan navegar productos, agregar al carrito, calcular envío, pagar con tarjeta de forma segura (sin exponer datos de tarjeta) y recibir confirmación inmediata por email con su factura.

Usuarios administradores

Necesitan gestionar productos, inventario, pedidos, devoluciones y usuarios desde un panel confiable. Requieren que los estados de los pedidos se actualicen correctamente, que las notificaciones se envíen al cliente y que los datos sean consistentes entre los diferentes módulos del sistema.

Procesos de negocio

El sistema debe soportar el flujo completo de venta en línea: desde la captación del usuario (registro + verificación) hasta la entrega del producto (tracking + confirmación). La calidad se mide en la capacidad del software de ejecutar estos procesos de manera correcta, manteniendo la integridad del inventario, la seguridad de los pagos y la trazabilidad de cada transacción. Un fallo en el proceso de login impide ventas; un fallo en el proceso de pedido genera pérdidas económicas y de confianza.

6. Modelos y Estándares Aplicables

ISO/IEC 25010:2023 — Modelos de Calidad de Producto de Software

El estándar ISO/IEC 25010:2023 define 9 características de calidad del producto de software. Para PuraLino se seleccionaron 5 de estas características como pilares del aseguramiento de calidad.

Contribución al proyecto:

  • Marco de evaluación estructurado: ISO 25010 proporciona un vocabulario y una taxonomía compartidos para definir, medir y comunicar la calidad del software entre el equipo de desarrollo.
  • Trazabilidad de requisitos: Cada requisito no funcional del sistema se vincula directamente a una característica ISO 25010, asegurando que ningún aspecto de calidad quede sin cobertura.
  • Métricas medibles: Las subcaracterísticas del estándar guían la definición de métricas concretas y verificables (secciones 4 y 5), evitando criterios subjetivos de calidad.
  • Mejora continua: Al evaluar periódicamente las métricas contra los umbrales definidos, el equipo puede identificar áreas de mejora y priorizar esfuerzos de desarrollo.

7. Administración de la Calidad

La calidad se gestiona durante el ciclo de desarrollo mediante las siguientes actividades:

ActividadDescripción
Revisiones de código Cada cambio se revisa antes de ser integrado a la rama principal. Se verifica que siga los patrones establecidos (MVC, Observer, Strategy) y que incluya validaciones tanto en frontend como en backend.
Pruebas funcionales Se ejecutan pruebas manuales del flujo completo de login (registro → verificación → login → logout) y pedido (carrito → checkout → pago → confirmación) en cada release, usando el entorno sandbox de Mercado Pago con tarjetas de prueba.
Auditorías de seguridad Se verifica periódicamente que: no se almacenan datos de tarjeta, los tokens JWT expiran correctamente, las contraseñas están hasheadas, los datos sensibles se limpian al cerrar sesión, y el middleware de autorización protege las rutas correctas.
Control de versiones Se utiliza Git con repositorios separados para frontend (PuraLinoMVC) y backend (PuraLinoMVC-api). Cada cambio se documenta con commits descriptivos. El Service Worker usa versionamiento de caché (puralino-cache-v15) para controlar actualizaciones del frontend.
Monitoreo en producción Se utilizan los logs de Render Dashboard para monitorear errores HTTP, tiempos de respuesta y disponibilidad del API. Los console.log estratégicos en el backend permiten rastrear el flujo de pagos y autenticación.
Mejora continua Los errores reportados por usuarios y detectados en logs se documentan, se diagnostica la causa raíz y se implementa la corrección mínima necesaria. Ejemplo reciente: se detectó que datos de pago persistían entre sesiones de usuarios, se implementó limpieza completa en logout y apertura de checkout.

9. Atributos de Calidad

Los siguientes 5 atributos de calidad se consideraron y aplicaron en los procesos de Login y Pedido:

1. Confidencialidad

Importancia: Los procesos de login y pedido manejan datos altamente sensibles (contraseñas, datos de tarjeta, información personal). Cualquier filtración compromete la confianza del usuario y la viabilidad del negocio.

Implementación: Contraseñas hasheadas con bcrypt (nunca almacenadas en texto plano); datos de tarjeta tokenizados por MP Payment Brick (nunca tocan nuestro servidor); JWT como mecanismo stateless que no expone datos en cookies; limpieza de formularios y localStorage al cerrar sesión; variables de entorno para credenciales de servicios externos.

2. Integridad

Importancia: En el proceso de pedido, es crítico que los totales calculados, el stock decrementado y los estados de los pedidos sean correctos y no puedan ser manipulados por el usuario.

Implementación: Cálculo de totales siempre en el backend (no se confía en montos enviados por el frontend); validación de stock en servidor antes de decrementar; registro de movimientos de inventario (StockMovement) para auditoría; doble validación de campos obligatorios (frontend + backend); tokens criptográficos firmados (JWT) que no pueden ser alterados.

3. Disponibilidad

Importancia: Si el sistema de login o de pedido no está disponible, el negocio pierde ventas directamente. Los usuarios esperan poder comprar en cualquier momento.

Implementación: Service Worker con caché de assets para carga offline; restauración de sesión desde caché local ante errores de red; carrito persistido en localStorage con expiración; despliegue en Render con auto-restart; manejo graceful de errores con mensajes claros al usuario en lugar de pantallas en blanco.

4. Usabilidad

Importancia: Un flujo de login o compra confuso genera abandono. En e-commerce, cada paso adicional o error no comunicado reduce la conversión.

Implementación: Login flexible (usuario o email); prefill automático de datos en checkout; dropdowns geográficos dinámicos (departamento → ciudad); cotización de envío en tiempo real; Payment Brick embebido con UX nativa de Mercado Pago; mensajes de validación específicos en español; modal de accesibilidad configurable; descarga de factura como PDF.

5. Modularidad

Importancia: La capacidad de modificar un componente sin afectar otros es esencial para la evolución del sistema. Agregar nuevos métodos de pago o cambiar el servicio de email no debe requerir reescribir el flujo de pedido.

Implementación: Patrón MVC con tres capas independientes; patrón Strategy para pagos (agregar nuevo método = agregar nueva estrategia); patrón Observer para comunicación por eventos; rutas backend modulares (un archivo por recurso REST); middleware de auth reutilizable y composable; servicio de email independiente del flujo de pedido (fire-and-forget).

11.2 Proceso: Proceso de Pedido

ITEMDESCRIPCIÓN
IDRNF-P01
CATEGORÍASeguridad (ISO 25010)
DESCRIPCIÓN DEL REQUISITOLos datos de tarjeta de crédito/débito no deben ser almacenados, procesados ni transitados por el servidor de la aplicación. La tokenización debe realizarla un tercero PCI-compliant. Los datos de pago deben limpiarse del DOM entre sesiones.
MÉTRICA O CRITERIO DE ACEPTACIÓN0 campos de tarjeta en logs, base de datos o payloads del backend; tokenización exclusiva vía Mercado Pago Payment Brick; 100% de limpieza de datos de pago al abrir checkout y al cerrar sesión
PRIORIDADAlta
COMENTARIOS / JUSTIFICACIÓNEl cumplimiento PCI-DSS se logra delegando la captura de datos de tarjeta al Payment Brick de Mercado Pago, que genera un token. Nuestro backend solo recibe y procesa tokens, nunca datos de tarjeta. Se implementó limpieza completa de formularios al abrir checkout y al cerrar sesión para prevenir filtración entre sesiones.
ITEMDESCRIPCIÓN
IDRNF-P02
CATEGORÍAAdecuación Funcional (ISO 25010)
DESCRIPCIÓN DEL REQUISITOEl sistema debe ejecutar el flujo completo de pedido: validar stock, calcular totales (subtotal, descuento, envío, gift card), procesar pago, crear orden, decrementar inventario, registrar movimiento de stock y enviar confirmación por email.
MÉTRICA O CRITERIO DE ACEPTACIÓNTasa de pedidos completados sin error ≥ 90%; integridad de inventario 100% (todo pedido genera StockMovement); email de confirmación enviado en ≥ 95% de pedidos
PRIORIDADAlta
COMENTARIOS / JUSTIFICACIÓNEl proceso de pedido es el flujo de negocio más crítico. Cada paso (validación, cálculo, pago, stock, email) debe completarse correctamente o el sistema debe revertir/notificar. Se implementaron validaciones exhaustivas en backend y registro de movimientos de stock para auditoría.
ITEMDESCRIPCIÓN
IDRNF-P03
CATEGORÍAFiabilidad (ISO 25010)
DESCRIPCIÓN DEL REQUISITOEl carrito de compras debe persistir entre recargas de página con una expiración automática de 24 horas. El formulario de pedido debe prevenir envíos duplicados y manejar errores de pago sin perder los datos ingresados.
MÉTRICA O CRITERIO DE ACEPTACIÓNCarrito persiste tras recarga (100%); expiración automática a las 24h; 0 pedidos duplicados por doble click (guard implementado); datos del formulario preservados tras error de pago
PRIORIDADAlta
COMENTARIOS / JUSTIFICACIÓNUn carrito que se pierde al recargar genera abandono. Un doble submit genera cobros duplicados. Se implementó persistencia en localStorage con timestamp, variable orderSubmitting como guard contra doble click, y el callback onSubmit del Brick maneja errores sin cerrar el formulario.
ITEMDESCRIPCIÓN
IDRNF-P04
CATEGORÍACapacidad de Interacción (ISO 25010)
DESCRIPCIÓN DEL REQUISITOEl formulario de checkout debe prellenar datos del usuario, ofrecer selección geográfica dinámica (departamento → ciudad), mostrar cotización de envío en tiempo real y proporcionar feedback visual durante el procesamiento del pago.
MÉTRICA O CRITERIO DE ACEPTACIÓNPrefill automático de 4 campos (nombre, email, dirección, teléfono); 33 departamentos y ciudades dinámicas disponibles; cotización de envío en ≤ 2s; botón de pago muestra "Procesando..." durante la transacción
PRIORIDADMedia
COMENTARIOS / JUSTIFICACIÓNReducir la cantidad de datos que el usuario debe escribir manualmente aumenta la conversión. La selección geográfica dinámica (departamento filtra ciudades) evita errores de escritura. El feedback visual durante el pago reduce la ansiedad del usuario y previene doble clicks.
ITEMDESCRIPCIÓN
IDRNF-P05
CATEGORÍAMantenibilidad (ISO 25010)
DESCRIPCIÓN DEL REQUISITOLos métodos de pago deben estar implementados bajo el patrón Strategy, permitiendo agregar nuevos métodos sin modificar el flujo de pedido existente. Las rutas de pago deben ser independientes de las rutas de pedido.
MÉTRICA O CRITERIO DE ACEPTACIÓNAgregar un nuevo método de pago requiere cambios en ≤ 2 archivos (payment.js + payments.js); 0 modificaciones al flujo de checkout existente; rutas /payments y /orders en archivos separados
PRIORIDADMedia
COMENTARIOS / JUSTIFICACIÓNEl patrón Strategy encapsula la lógica de cada método de pago en un objeto independiente. Si se necesita agregar Nequi, Daviplata u otro método, basta con agregar una nueva estrategia en el frontend y un handler en el backend, sin modificar el código del carrito, checkout ni facturación existente.
